資料類：消失、不一致、衝突

沒定義 → 發生什麼
  • 資料存 localStorage，重整消失
  • 兩個人同時預約同一時段
  • 前端顯示的時段跟後端不同步
有定義 → 應該怎樣
  • 指定 Google Sheet 作為唯一資料源
  • 後端鎖定時段，寫入前再檢查一次
  • 前端每次從後端拉最新狀態

安全類：Key 外洩、重複提交

沒定義 → 發生什麼
  • API Key 寫在前端 JavaScript 裡
  • 按鈕連點三次 → 三筆重複預約
  • 任何人都能打 admin 端點
有定義 → 應該怎樣
  • Key 只放在 GAS 後端 PropertiesService
  • 提交後停用按鈕 + 後端去重
  • admin 端點加 Key 驗證

架構 + AI：混亂、矛盾、改壞

沒定義 → 發生什麼
  • 前後端邏輯混在同一個檔案
  • AI 第一次用物件、第二次用陣列
  • 加功能時跟原有邏輯衝突
有定義 → 應該怎樣
  • 前端只管顯示、後端只管邏輯
  • API 端點和資料格式寫死在規格裡
  • 加功能前先更新 spec，再讓 AI 照做

範圍 + 驗證：失控、無效

沒定義 → 發生什麼
  • 「順便加個評分功能」→ 系統越長越大
  • 過期時段還能選
  • 預約成功但沒有任何確認
有定義 → 應該怎樣
  • spec.md 列出功能邊界，超出範圍不做
  • 後端驗證時段是否在未來 + 是否可用
  • 預約後觸發 Email 通知雙方

# 諮詢預約系統 spec.md

## 功能需求
- 顯示可預約時段（排除已過期、已被預約的）
- 預約（填姓名 + Email + 選時段）

區塊二：技術選型

spec.md — 技術選型

- 通知：GmailApp

區塊四：API 端點

spec.md — API 端點
## API 端點
- GET /slots
  → 取得可預約時段（自動排除過期 + 已預約）

- POST /book
  → 預約（帶時段ID + 姓名 + Email）
  → 寫入 Sheet + 寄確認信

- GET /admin?key=xxx
  → 講師查看預約清單

三支 API，職責分明
前端只呼叫 API、後端只處理邏輯
這就是 R1 缺少的「分工」

區塊五：安全規則

spec.md — 安全規則
## 安全規則
- 後端驗證時段是否仍可預約（不信任前端）
- 同一 Email 同一時段不能重複預約
- admin 端點需要 Key 驗證

這段最容易被忽略

安全規則不寫 → AI 不會主動幫你想
